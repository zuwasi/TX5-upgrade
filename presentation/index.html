THREADX MIGRATION · 03

Change one thing per stage

So every difference has exactly one cause

StepKernelCore / ABIApplication source
Stage 1 → 2TX5.6 → TX6.5Cortex-M4 unchanged; soft-float → hard-floatUnchanged
Stage 2 → 3TX6.5 unchangedCortex-M4 → Cortex-M85Unchanged
SupplementTX6.5 unchangedCortex-M55: newest core this QEMU runsUnchanged
  • Stage 1 → 2 isolates the RTOS migration on the core the TX5 kernel was built for.
  • Stage 2 → 3 isolates the CPU port change on an unchanged kernel release.
  • M55 shares the Armv8.1-M port family with M85, so it is the closest runnable proxy, not a substitute for M85 execution.
The float ABI change in stage 1 → 2 is forced by the TX5 archive, not chosen. It is called out as its own diff later.

THREADX MIGRATION · 06

Where the ThreadX 5 kernel comes from

TX5 was never open source; the WICED SDK ships it as binaries

  • The public WICED SDK 3.1.0 contains ThreadX 5.6 headers and ThreadX.ARM_CM4.release.a.
  • Its README restricts those objects to WICED use, so nothing from the SDK is in this repository.
  • The build links the archive from TX5_ROOT, a separate checkout; configuration fails if TX5_ROOT is inside the repository.
  • CI clones the same SDK commit into the runner's temp directory for every run.
THREADX MIGRATION · 07

Reading a binary-only kernel

No source, so inspect build attributes, symbols and machine code

  • No VFP tag: the archive is soft-float, so every object in the image must be soft-float.
  • Packed enums: GCC -fshort-enums; Clang must match it.
  • The CM4 archive is the Cortex-M3 port: it never saves FPU registers.
  • Unresolved WICED hooks show exactly what the board layer must provide.

THREADX MIGRATION · 10

The most modern runnable QEMU Cortex-M here

Probe the installed executable instead of relying on development docs

M55 is the newest Cortex-M CPU exposed by this installed QEMU build. QEMU development documentation mentions AN555, but it is not in the tested binary.

An M85 image is never run under an M55 CPU and labelled M85. The M85 ELF remains a separate, explicitly unexecuted build artifact.
THREADX MIGRATION · 11

Licensing is an engineering input

Public on GitHub does not mean free to redistribute

  • The WICED SDK README limits its ThreadX / NetX objects to use with WICED.
  • The TX5 archive and headers are linked from an external checkout and never committed or published.
  • The application, board layer, adapter and tests are independently written; original work is MIT.
  • ThreadX 6.5 is pinned as an MIT submodule with its upstream notices.
  • PDF typography embeds Roboto under OFL 1.1, with the notice shipped beside the PDF.
This is an engineering demonstration, not a legal opinion on WICED licence scope. Product use of a TX5 kernel needs its own licence.

THREADX MIGRATION · 15

Diff 1: how each kernel enters the build

Imported binary archive vs rebuilt source

With source, the kernel is recompiled for the application's ABI and configuration. With a binary, the application must adopt the archive's ABI and configuration instead.

THREADX MIGRATION · 16

Diff 2: the float ABI is dictated by the archive

Hard-float objects cannot link against this TX5 kernel

  • A hard-float task on this TX5 port would break: it saves no s16-s31 and always returns with a non-FP EXC_RETURN.
  • Stage 2 is therefore also the first point where FPU code becomes safe on M4.
  • The image attributes confirm it: TX5 has no FP_arch tag; TX6 M4 has VFPv4-D16 and AAPCS VFP.
THREADX MIGRATION · 17

Diff 3: vectors and the first context switch

TX5.6 starts threads through SVC, TX6 does not

Leaving SVC at the TX6 default fault handler makes TX5 hang before the first thread runs. The verifier treats that as a timeout failure.
THREADX MIGRATION · 18

Diff 4: low-level init and the idle hook

Contracts recovered from disassembly, implemented in MIT code

  • The TX5 port objects reference _tx_thread_system_stack_ptr; the TX6 Cortex-M4 port sources do not use it.
  • The WICED idle loop calls tx_low_power_enter, which calls platform_power_down_hook(ticks to next timer).
  • A non-zero return is added to the kernel clock (tickless mode). Returning 0 keeps normal ticking.
THREADX MIGRATION · 19

Diff 5: a 4-byte configuration bug

Found by the metrics, then made impossible to build

The kernel cleared 4 bytes past each 176-byte thread object. led_thread_stack follows led_thread in RAM, so its first fill word was zeroed and the stack scan reported a full stack. The functional test still passed: only the measurement exposed the corruption.

With a binary kernel, the header configuration is part of the ABI. It must be the configuration the archive was built with, and it should be asserted.

THREADX MIGRATION · 21

Diff 7: milliseconds versus RTOS ticks

Keep units visible; avoid a silent tenfold delay error

The tested board clock constants are 25 MHz for MPS2-M4 and 32 MHz for MPS3-M55. The M85 build reuses the demonstration map and clock; a real M85 SoC must replace them.

QEMU icount is synthetic: 128 ns per emulated instruction. The tick invariant is a scheduler test, not a physical time or jitter guarantee.
THREADX MIGRATION · 22

Diff 8: preserve the held-button latch

A subtle behavioural detail, checked at release as well as press

The verifier deliberately rejects a cycle-4 OFF result.
THREADX MIGRATION · 23

Diff 9: startup assembly under Clang

A real encountered failure, with a trace-supported fix

QEMU traced a bus fault at 0x00080000 during the endless startup copy. The replacement uses explicit comparisons, copies .data, clears .bss and enables CP10/CP11.

THREADX MIGRATION · 24

Diff 10: TX6 security mode and BSP scope

Scope down the first proof; make omitted features explicit

  • Single-secure avoids exercising secure-stack paths without a non-secure image.
  • Do not infer a TrustZone security policy from a successful boot.
  • A real M85 SoC has its own memory map, clocks, IRQ routing, caches and MPU.
THREADX MIGRATION · 25

Diff 11: success is a checked contract

Fail on missing, wrong or partial output

A TX6 image cannot pass as a TX5 run: the expected version is per stage and must match exactly. CMake also refuses a TX5 build on any core but M4, or with TX5_ROOT inside the repository.

THREADX MIGRATION · 26

The RTOS services really switch tasks

A higher-priority worker must preempt, suspend, resume and signal

  • The progress flag is application state, so the check does not depend on TCB internals.
  • The timer wakes the sleeping LED task nine times through each kernel's real timer path.
  • Mutex and pool checks are basic operations, not contention or fragmentation stress.

THREADX MIGRATION · 32
Stack headroom is measured, not assumed
The same fill-pattern scan on both kernels
TX5 M4 196 B, TX6 M4 224 B, TX6 M55 360 B. Differences come from the ABI, compiler code generation and each port's stack frame; they are not attributed to one cause.
Production worst-case paths, nested interrupts, FPU/MVE context and M85 behaviour still require stress and hardware validation.


THREADX MIGRATION · 33
Performance chart: emulator test cost
Measure what was run, and say what the number means
TX5 looks faster because its idle hook executes WFI, which QEMU skips to the next timer, while TX6 idles in a spin loop that QEMU must emulate. This is idle strategy, not kernel speed.

THREADX MIGRATION · 36
What the M85 build proves
Correct target attributes and resolved symbols, not execution
Clang compiled and LLD linked the unchanged application with the M85 port. The demo linker map and clock are not a production M85 SoC definition.
There is no M85 runtime, performance, power, PACBTI or mixed FPU/MVE correctness result.

THREADX MIGRATION · 39
The technical conclusion
A bounded yes, backed by executable evidence
  • YES: the application runs unchanged on the real ThreadX 5.6 Cortex-M4 kernel and on ThreadX 6.5.
  • YES: behaviour, service checks and every tick match between TX5 and TX6 on the same core.
  • YES: the same application compiles and links with the upstream Cortex-M85 port.
  • LEARNED: with a binary kernel, its ABI and header configuration are part of the contract.
  • NOT YET: M85 runtime and real-board BSP / timing / security qualification.
Next: choose the target M85 SoC and run the hardware acceptance suite, including a TX5-vs-TX6 cycle comparison on M4 silicon if that baseline matters.
